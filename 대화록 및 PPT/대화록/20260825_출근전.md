### 그런데 "예측"이 실행 중에 일어나진 않습니다

시뮬 루프는 `replay_isaac.py:259-260` 처럼 `JOINTS[t]`를 그냥 순서대로 관절 목표로 던지는 구조입니다. Isaac Sim 안에 정책이 들어가 있지 않아요.

추론은 **별도 머신에서 미리, open-loop로** 끝났습니다 (`/root/policy_rollouts/`). 즉 정책에 넣은 관측이 실시간 시뮬 카메라 영상이 아니라 **녹화된 데이터셋 관측**입니다. 8/24 랩미팅 자료에도 그렇게 써 두셨습니다:

> "아직 open-loop: 정책이 보는 관측은 녹화본이라, 실행 중 큐브를 옮겨도 모른다. 실시간 카메라 관측으로 도는 closed-loop 가 다음 단계"
> — `make_labmeeting_pptx_0824.py:574`

### 정리하면

- **궤적 = 예측 맞음** (학습된 정책 출력)
- **실행 = 재생** (미리 뽑은 600프레임을 순차 명령)
- **물리는 진짜** — 큐브 파지·운반·안착은 PhysX가 실제로 계산하므로 7.8 mm는 유효한 수치
- **닫혀 있지 않음** — 실행 중 큐브를 옮기면 정책은 그대로 원래 궤적을 따라갑니다

"모델이 스스로 보고 판단하며 움직인다"고 말하려면 다음 단계인 closed-loop(시뮬 카메라 → 정책 → 관절 명령 루프)가 필요하고, 로드맵상 이번 주 항목으로 잡혀 있습니다. 8/24에 추가된 `wristcam_probe.py` 의 카메라 정합 작업이 바로 그 선행 작업이고요.

### 1. 지금 closed-loop가 안 되는 이유

**① 시뮬 루프 안에 정책이 없습니다 (구조적 이유)**

`replay_isaac.py:256-262`의 실행 루프:

```
for t in range(T):
    ctrl.apply_action(ArticulationAction(joint_positions=JOINTS[t], ...))
    set_gap(gap_of(GRIP[t]))
    world.step()
```

`JOINTS`는 시작 전에 npz에서 통째로 읽어둔 600×6 배열입니다. 루프 안에 관측→추론→명령이 없고, 인덱스 `t`만 증가합니다. **재생기지 제어기가 아닙니다.**

**② 관측을 만들 수단이 없었습니다 (어제 해결됨)**

정책 입력은 `observation.images.camera1`(손목캠) + `camera2`(정면캠) 640×480 2뷰 + state입니다. 그런데 `replay_isaac.py:220`에 있는 카메라는 `Camera("/World/cam", resolution=(1280, 720))` 하나뿐 — **영상 녹화용**이지 정책 관측용이 아닙니다. 해상도도 마운트도 학습 규약과 다릅니다. 이게 8/24에 끝낸 STEP 5-1/5-2입니다.

**③ 추론 환경이 물리적으로 분리돼 있습니다**

| 위치 | 있는 것 |
|---|---|
| 컨테이너 | ACT 체크포인트 `/root/train_m1013_act_v6`, lerobot |
| 호스트 | Isaac Sim, `/home/kim/m1013/` |

**④ 큐브가 궤적 전용 위치에 스폰됩니다**

`replay_isaac.py:184-188`이 큐브를 `DATA["cube_pick"]`에 놓습니다. 즉 **"궤적에 맞춰 큐브를 배치"**하는 구조예요. 순서가 거꾸로입니다.

### 2. closed-loop를 만들려면

```
매 스텝 (또는 청크마다):
  1. 손목캠·정면캠 640×480 렌더        ← cameras_v6match.json
  2. state 구성                        ← ⚠️ 아래 주의
  3. 브릿지로 정책에 전송 → 액션 청크 수신
  4. 청크를 관절 목표로 실행
  5. K프레임 후 1번으로 재계획
```

**⚠️ 놓치기 쉬운 함정 — state 규약**

`convert_v6_m1013.py:114`:

```python
st_j = np.vstack([ac_j[:1], ac_j[:-1]])  # state[t] = action[t-1]
```

정책은 **"직전에 내가 명령한 값"**을 state로 보도록 학습됐습니다. 실제 측정 관절각이 아닙니다. closed-loop에서 Isaac의 `get_joint_positions()`를 그대로 넣으면 학습 때 본 적 없는 입력이 들어가 조용히 성능이 떨어집니다.

**결정할 것 3가지**:

| 항목 | 권장 |
|---|---|
| 추론 위치 | ZMQ 소켓 브릿지 (※ 이후 LeRobot async_inference로 정정됨) |
| 재계획 주기 | 청크 100프레임 전부 실행하지 말 것 |
| 렌더 속도 | 2뷰 렌더 포함 스텝 시간부터 실측 |

### 3. 큐브 위치가 바뀌어도 잡게 하려면

**closed-loop는 필요조건이지 충분조건이 아닙니다.**

**① 정책이 위치를 배웠는가 — 확인해봤습니다**

replay npz 8개의 큐브 위치:

| | X 표준편차 | Y 표준편차 | X 범위 | Y 범위 |
|---|---|---|---|---|
| pick | 33.6 mm | 35.2 mm | 119 mm | 117 mm |
| place | 68.8 mm | 26.2 mm | 221 mm | 73 mm |

**희소식입니다.** 데모마다 큐브 위치가 실제로 달랐고, 정책은 그 159개를 모방하며 학습했습니다. 다만 학습 분포는 pick 기준 대략 ±60mm 창입니다. ACT는 모방학습이라 본 적 없는 위치로 외삽하지 않습니다.

**② 시각 도메인 갭** — 아직 미측정. 5-3의 첫 산출물입니다.

**③ 재계획 주기 — "실행 중 이동"에 답하는 부분**

| 재계획 주기 | 반응 시간 | 성격 |
|---|---|---|
| 100프레임 (청크 전부) | 3.3초 | 시작 위치만 반영 |
| 20~25프레임 | 0.7~0.8초 | 실용적 절충 |
| 매 스텝 + temporal ensembling | 즉시 | ACT 논문 방식 |

### 검증 실험 제안

- 같은 8ep을 **원래 큐브 위치**로 → GT 재생(6/8 성공) 대비 A/B → 순수 도메인 갭
- 같은 ep을 **큐브만 ±30/60/100mm 격자로 이동** → 성공률 곡선 → 위치 일반화 범위

### 1. 설계서가 제대로 짚은 것

**이미지-액션 임베디먼트 불일치는 실재하는 문제이고, 문헌이 뒷받침합니다.**

**val/test 부재 지적은 SmolVLA와 무관하게 가장 중요한 부분입니다.**

**SmolVLA가 관절 액션을 받을 수 있다는 1.4의 답도 맞습니다.** 액션을 32차원으로 패딩하고 추론 시 원래 차원으로 잘라냅니다. "50 에피소드 최소" 권장치도 실제 문서와 일치합니다.

### 2. 비판 — 심각도 순

**① 갭을 하나 없애고 다른 갭을 만듭니다 (가장 큰 문제)**

|---|---|---|---|

**답: 시연 수집 비용의 비대칭**

M1013은 직접교시가 됩니다(cockpit 버튼 + 6축 토크센서). 그러니 "불가능"은 아닙니다. 하지만 **33kg 산업용 암을 손으로 끌어서 200회**와 **소형 리더-팔로워 리그로 200회**는 비용이 완전히 다릅니다.

> **값싼 교육용 플랫폼에서 대량 시연을 모으고, 비싼 산업용 암에서는 최소한의 실기 데이터만으로 갭을 닫는다.**

이건 설계서 7.5의 E4가 가리키던 서사와 같습니다. 다만 설계서는 이걸 *선택 실험*으로 뒀는데, **사실 이게 프로젝트 전체의 존재 이유**입니다.

**공부하실 것 — MimicGen** (CoRL 2023). 사람 시연 약 200개로 18개 태스크 5만+ 데모 생성. 사람 시연은 **비싼 씨앗(seed)**, 나머지는 **변환으로 생성**. 여러분 파이프라인을 이 언어로 다시 쓰면 OMX 시연 = 씨앗, IK 리타게팅 + Isaac 렌더 = 생성.

**정직하게 남는 약점**: "스크립트로 궤적을 만들면 되지 않나"는 여전히 유효한 반론입니다. 주장하려면 A/B를 하나 넣으세요.

### 3. 색상 조건 계획 — 방향은 아주 좋습니다

**좋은 소식**: 이게 들어가면 SmolVLA를 쓸 이유가 생깁니다.

**나쁜 소식**: 문헌상 이 설정의 실패 대부분은 파지 실패가 아니라 **타깃 선택 오류**입니다.

지켜야 할 규칙:

**① 매 에피소드에 방해 물체가 반드시 있어야 합니다** — 큐브 하나만 있으면 지시를 안 읽어도 풀립니다.

**② 색과 위치를 반드시 교차시켜야 합니다** — 파랑이 늘 왼쪽이면 정책은 색이 아니라 **위치**를 배웁니다. 그리드가 **`색 × 위치` 요인 설계**가 됩니다.

**③ 기존 159개는 언어 학습에 기여하지 않습니다** — 전부 파란 큐브 단일 지시.

**④ 평가 지표를 분리하세요**

```
타깃 선택 정확도  : 지시한 색을 집었는가        ← 언어 접지 능력
파지 성공률      : 집으려던 것을 실제로 집었는가  ← 조작 능력
태스크 성공률    : 둘 다 성공
```

**⑤ 홀드아웃은 조합으로** — "빨간 큐브를 셀 C3에서" 같은 **학습에 없던 색-위치 조합**을 test로.

### 1. 로봇에 모델 업로드는 안 됩니다

두산 컨트롤러는 **모션 컨트롤러**입니다 — GPU 없음, DRL은 모션 언어, 폐쇄형이라 PyTorch 설치 불가. `dsr_driver`도 **외부 PC에서 돌면서 이더넷으로 통신**하는 구조입니다.

### 2. 그런데 PC가 가까울 필요도 없습니다 — LeRobot에 이미 있습니다

```
[로봇 옆]  RobotClient  ──── gRPC ────>  PolicyServer  [기존 PC, 5070 Ti]
           카메라 읽기                      추론
           로봇 제어      <─── 액션 청크 ───
```

원격이 예외가 아니라 **설계 의도**입니다. 정책이 다음 청크를 계산하는 동안 로봇은 현재 청크를 계속 실행합니다.

**대역폭** (기본값 기준): 관측 전송 0.83초에 한 번 × 1.84MB = **약 18 Mbps**. 유선 LAN은 물론 **WiFi로도 됩니다.**

**메모리**: SmolVLA 추론 시 **약 2GB** (PI0는 14GB).

### 3. 세 가지 구성

| 구성 | 로봇 옆 | 원격 | 추가 비용 |
|---|---|---|---|
| **A. 원격 추론** ⭐ | 노트북 (카메라+제어) | 기존 PC | **0원** |
| B. Jetson | Orin Nano 8GB | 학습만 | 약 35만원 |
| C. 전부 로봇 옆 | GPU 노트북/미니PC | — | 높음 |

**로봇 옆에 반드시 있어야 하는 건 카메라뿐입니다.**

**② Real-Time External Control** — UDP 최대 1kHz, `servoj_rt`/`speedj_rt`/`torque_rt`, ⚠️ **실시간 OS 필요**

## 🤖 Claude

**🔧 WebFetch / WebSearch** ×3 — Doosan RT 매뉴얼(404 → github.io 우회), RT API 시퀀스, PREEMPT_RT 요구사항

가능합니다. 다만 조건이 넷이고, 그중 하나는 지금 확인할 수 없습니다.

### 필요 조건 4가지

**① 컨트롤러 펌웨어가 UDP RT API를 지원해야 함** — *"안정적인 네트워크 조건과 UDP 기반 RT API를 지원하는 컨트롤러 버전이 필요"*. **로봇 도착하면 가장 먼저 확인.**

**② 로봇 옆 PC에 PREEMPT_RT 커널** — 두산 매뉴얼: *"외부 컨트롤러에 실시간 OS를 사용해 실시간 환경으로 구축해야 전체 시스템의 실시간성이 보장된다."* **좋은 소식**: PREEMPT_RT가 2024년 9월 커널 6.12에 메인라인 병합.

**③ 로봇과 직결 이더넷** — 예제 `connect_rt_control("192.168.137.100", 12348)`는 직결 대역.

**④ 로봇 옆 PC가 리눅스**

### RT를 써도 원격 추론 구조는 그대로입니다

```
[기존 PC]   추론 (약 1Hz)  ──gRPC──┐
                                    ▼
[로봇 옆 RT 리눅스]  액션 큐 → 보간 → servoj_rt 1kHz ──UDP직결──> M1013
```

주기가 1000배 다르니 충돌하지 않습니다. **부수 효과**: 30Hz를 1kHz로 보간하면 움직임이 더 매끄러워집니다.

```
connect_rt_control(host, port) → set_rt_control_input/output(...)
→ start_rt_control() → loop: read_data_rt() / servoj_rt(...) / write_data_rt()
→ stop_rt_control() → disconnect_rt_control()
```

### 실제 비용

**노트북에서 RT 지터 잡기가 까다롭습니다** — SMI, C-states, 터보 부스트를 BIOS에서 끌 수 있어야 하는데 소비자용 노트북은 옵션이 없는 경우가 많습니다.

### 언제 필요해지나

토크 제어 확장 / 속도 기반 정책 / 30Hz 지터가 실제로 관측될 때 / 더 빠른 동작. **넷 다 지금은 아닙니다.**

### 중간 경로

**RT 커널 없이도 RT API 자체는 동작합니다.** 일반 커널에서 100~250Hz로 시도 → 지터 실측 → 문제 되면 그때 RT 커널. **측정하고 나서 결정하는 순서**가 맞습니다.

### 1. 네, 이런 식으로 합니다 — 정석의 한 변형

문헌에 거의 같은 프레이밍의 연구가 있습니다. "값싸고 텔레오퍼레이션이 쉬운 플랫폼 → 시연 수집이 비싼 고페이로드 산업용 암". OMX → M1013 그대로입니다.

RT-X는 더 중요한 걸 보여줍니다 — **cross-embodiment 데이터는 타깃 로봇 데이터가 부족할 때 특히 효과가 큽니다.** M1013 데이터를 20~50개밖에 못 모으는 상황이 정확히 그겁니다.

### 2. 그런데 정직하게 — 가장 단순한 길은 OMX를 거치지 않습니다

> "M1013이 큐브를 집게 하고 싶다"만이 목표라면 → M1013에서 직접 50개 모아 fine-tune. 끝.

그러니 질문을 바꿔야 합니다. **"왜 굳이 먼 길을 가는가?"** 답은 하나 — 만들려는 건 정책이 아니라 **"값싼 데이터로 비싼 로봇을 가르치는 방법과 그 효율 측정치"**입니다.

그래서 **E6(실기만 학습) 대조군**이 반드시 있어야 합니다.

### 3. 잘하고 있는가

**잘하고 있는 것**: 풀스택 완주(수집→IK→USD→물리→학습→평가) / 검증을 실제로 함(FK 2.12mm, 점프 3.22°, kNN 0/6000) / 자기 결과를 의심함(PnP 판단 착오 자인) / 문제를 터지기 전에 발견(카메라 키 스왑, 폴링, state 지름길)

**약한 것**: 검증셋 부재 → 0.62°의 의미 불명 / 대조군 부재 → 전이 효과 주장 불가 / 표본 1건

**솔직한 리스크**: RT-X는 모델 용량이 작으면 이종 데이터를 제대로 못 쓴다는 것도 보여줬습니다. SmolVLA는 450M로 작은 편입니다. 가장 가능성 높은 결과는 "실기 데이터가 지배적이고 OMX 기여는 측정은 되나 크지 않다"입니다. **그래도 그건 답입니다.** 진짜 실패는 대조군이 없어 왜 되는지 말을 못 하는 것입니다.

| 제가 잘못 말한 위험 | 실제 위험 |
|---|---|
| "정책이 실물에서 동작하지 않는다" | **"sim 사전학습이 실기 fine-tune에 이득을 주지 못한다"** |


**모델은 OMX 영상을 단 한 장도 보지 않습니다.** OMX에서 오는 건 궤적(액션)뿐입니다.

3. 실물 M1013이 아직 없음
4. → Isaac에서 만들어냄
5. → **그 렌더가 학습 데이터의 전부**

**"sim을 이미지 공장으로 쓴다"와 "OMX 데이터를 쓴다"는 같은 말입니다.** 하나를 빼면 다른 하나도 빠집니다.
